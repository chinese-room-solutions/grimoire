# Tuesday 14 July

Release day for 2.11.0. Writing this up while it is fresh because the rollback
was avoidable and I want the sequence recorded.

## Morning

Cut the release branch at 09:40, tagged `v2.11.0-rc.3`, and the pipeline
deployed it to staging in eleven minutes. Smoke suite green. Ran the manual
checklist on the checkout flow because the automated coverage there is still
thin.

Rehearsed the schema change on a restored copy of production first — the new
`invoices.settled_at` column plus its backfill. Ninety seconds on a copy with
last night's data. The backfill is written to be resumable and it is idempotent,
which turned out to matter.

## The deploy

Promoted to production at 13:05. Canary at 5% for fifteen minutes, error rate
flat, latency flat. Went to 50% at 13:22, full at 13:31.

At 13:44 the alert for invoice write latency fired. p99 on the write path had
gone from 40ms to 2.1s, and it was climbing rather than settling. Customer
support had two tickets already.

Rolled back at 13:49. The rollback itself was clean — the previous version was
still the standby colour, so cutting traffic back took under a minute and the
error rate recovered immediately. That part of the process worked exactly as it
is supposed to, and it is the only reason this was a twenty-minute incident
rather than an afternoon. The mechanics are written up in
[[release-process#Rollback]].

## Cause

The backfill job was still running when the new code went to 100%. The new write
path takes a row lock the backfill also wants, and the backfill was doing 50k
rows per batch with no delay between batches. Under production write volume,
every invoice write queued behind a batch.

Neither half is wrong on its own. Nobody had thought about them overlapping,
because on staging the backfill finishes in ninety seconds and the overlap
window does not exist.

Two real mistakes:

1. The deploy was not gated on the migration job completing. It should have been
   a hard gate in the pipeline, not a note in the runbook.
2. The batch size was tuned against a database with no concurrent load.

## Afternoon

Rewrote the backfill: 2000 rows per batch, 100ms sleep, and it checks a kill
switch between batches so it can be stopped without a code change. Re-ran it
from where it had stopped — resumability paid for itself — and it finished at
17:20 with no measurable impact on write latency.

Redeployed 2.11.0 at 17:35, no canary this time since the code had already been
exercised at full traffic for thirteen minutes. Watched it for half an hour.
Fine.

## Follow-ups

- [ ] Pipeline gate: no promotion while a migration job for the same service is
      running. This is the actual fix.
- [ ] Every backfill from now on takes a batch size, a delay, and a kill switch.
      Add it to the template.
- [ ] The invoice write latency alert fired at 13:44 for a regression that
      started at 13:31. Thirteen minutes is too slow — the `for:` window is 10m
      and the threshold is too generous. [[monitoring#Alerts worth having]].
- [ ] Load-test the migration path against a copy with synthetic write traffic,
      not an idle copy. Half of the value of the rehearsal was lost to that.

Discussed most of this at standup the next morning, see
[[standup-notes#2026-07-15]].
